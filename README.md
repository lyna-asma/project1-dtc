# Digital Wallet and Merchant Payment Platform

A cash-to-digital wallet and merchant payment platform demo modelled on Algerian digital payment services.

> **Important Notice:** All money in this application is strictly fake and simulated. This project is a software demonstration and educational prototype. It is not affiliated with, nor connected to, any real-world bank, financial institution, or payment network.

---

## The Problem

In cash-dominant economies, many individuals earn and hold physical cash but lack convenient, accessible ways to make digital payments without formal bank accounts. This platform bridges cash and digital payments: customers hand physical cash to a local merchant shop, the shop credits the customer's digital wallet balance from its own pre-loaded balance, and the customer can then spend digital money at shops or send money to friends and family directly from their mobile phone.

---

## Users and Roles

The platform defines three distinct user roles:

- **Customer**
  - Sign up using a phone number and password with a simulated one-time verification code (OTP).
  - Hand physical cash to a registered merchant to receive digital credit in their wallet.
  - Pay a merchant by entering a single-use payment code generated by the shop and confirming with their password.
  - Send money directly to another customer by phone number, previewing the recipient's registered display name before confirming with their password (planned for a future version).
  - View their current wallet balance and personal transaction ledger history.

- **Merchant (a shop)**
  - Accept physical cash from a customer and credit the customer's wallet (deducted directly from the shop's own balance).
  - Generate single-use, 5-minute payment request codes for customer purchases.
  - View the shop's approval status (planned for a future version), current balance, and dedicated merchant transaction history.

- **Admin (the platform owner)**
  - Load digital funds into merchant shop balances (the sole entry point of money into the system).
  - Review and approve registered merchant shops before they can transact (planned for a future version).
  - Inspect all transactions across the entire platform.
  - Reverse a transaction by appending an offsetting transaction, provided the recipient still has sufficient balance (planned for a future version).

## Example Walk-Through

The following scenario traces the movement of funds across all roles with concrete numbers, demonstrating that total money in the system is conserved at every step.

### Initial State
All accounts start with zero balance:
- **Shop A:** 0 DA
- **Customer 1:** 0 DA
- **Customer 2:** 0 DA
- *Total System Balance:* 0 DA

---

### Step 1: Admin Loads a Shop
The admin loads **10,000 DA** into Shop A's balance.
- **Shop A:** 10,000 DA
- **Customer 1:** 0 DA
- **Customer 2:** 0 DA
- *Total System Balance:* 10,000 DA

---

### Step 2: Shop Adds Cash to a Customer's Wallet
Customer 1 hands **3,000 DA** in cash to Shop A. Shop A enters Customer 1's phone number and credits their wallet:
- **3,000 DA** is deducted from Shop A and added to Customer 1.
- **Shop A:** 7,000 DA (10,000 - 3,000)
- **Customer 1:** 3,000 DA (0 + 3,000)
- **Customer 2:** 0 DA
- *Total System Balance:* 10,000 DA

---

### Step 3: Customer Pays the Shop
Customer 1 purchases goods worth **1,200 DA** at Shop A. Shop A generates a payment code. Customer 1 enters the code, reviews the shop name and amount, and confirms with their password:
- **1,200 DA** is deducted from Customer 1 and added to Shop A.
- **Shop A:** 8,200 DA (7,000 + 1,200)
- **Customer 1:** 1,800 DA (3,000 - 1,200)
- **Customer 2:** 0 DA
- *Total System Balance:* 10,000 DA

---

### Step 4: Customer Sends Money to Another Customer (Planned for a future version)
Customer 1 transfers **500 DA** to Customer 2 by phone number. Customer 1 confirms Customer 2's registered name on screen and verifies with their password:
- **500 DA** is deducted from Customer 1 and credited immediately to Customer 2.
- **Shop A:** 8,200 DA
- **Customer 1:** 1,300 DA (1,800 - 500)
- **Customer 2:** 500 DA (0 + 500)
- *Total System Balance:* 10,000 DA (8,200 + 1,300 + 500 = 10,000 DA)

## Main Rules

1. **Balance Never Below Zero (`CHECK (balance >= 0)`):** A wallet balance can never become negative. Balance checks and deductions occur atomically within a single database transaction protected by row-level locking (`SELECT ... FOR UPDATE`). Any transaction that would result in a negative balance is rejected.
2. **The Three Centralized Limits (Planned for a future version):** Configured in a single central configuration file:
   - Maximum **50,000 DA** per transaction.
   - Maximum **100,000 DA** outgoing per customer per day.
   - Maximum wallet balance of **200,000 DA** per customer wallet.
3. **No Fees in Version 1:** All payments carry zero fees in version 1. Transactions are 1:1 between sender and recipient, with schema fields extensible for future fee structures.
4. **Simulated One-Time Code (OTP):** Account registration uses a simulated 6-digit one-time code. Code delivery is isolated behind a single replaceable function that logs or exposes codes in development/testing mode, avoiding external SMS costs while keeping automated tests deterministic.
5. **Whole Dinars Stored as Centimes:** User input and display values are whole Algerian Dinars (DZD). All database records and internal calculations store balances and amounts as integer centimes (`dinars * 100`) to completely eliminate floating-point rounding errors.
6. **Append-Only Ledger:** Transaction records are immutable. Rows are only ever added—never edited or deleted. Correcting an erroneous transaction requires an admin reversal that creates a new offsetting transaction (reversals are planned for a future version).

## How to Run the Whole System Locally (Docker Compose)

### Environment Variables
Environment settings are defined in `.env.example`:

| Variable | Description | Default in `.env.example` |
| :--- | :--- | :--- |
| `PORT` | HTTP port for the Express application server | `3000` |
| `DATABASE_URL` | PostgreSQL database connection string | `postgres://postgres:postgres@localhost:5432/wallet_db` |
| `JWT_SECRET` | Secret key used for signing and verifying JWT tokens | `dev-secret-key-change-in-production` |

To set up your local environment file:
```bash
cp .env.example .env
```
*(On Windows PowerShell: `Copy-Item .env.example .env`)*

### One-Command Docker Compose
Run the entire stack (PostgreSQL database, migrations, admin seeding, and Express application server) with:
```bash
docker compose up --build
```
This starts PostgreSQL, applies all Drizzle migrations, runs the idempotent admin seed script (`npm run seed:admin`), and serves the API on `http://localhost:3000`.

To start only the database in the background:
```bash
docker compose up -d db
```

### Running the Application Server Locally
Once dependencies are installed and the database is configured:
```bash
npm install
npm run dev
```
*(Server starts on `http://localhost:3000` and responds with `{"status":"ok"}` on `/health`).*

### How the Admin Account is Created
- Seeded via `npm run seed:admin` (or automatically during Docker container startup), creating the initial admin user with phone `0555000000`, password `Admin1234!`, role `admin`, and an initialized wallet. Repeated execution is idempotent.

### Where to See the Simulated One-Time Code
- When a customer or merchant registers via `POST /api/auth/register` and `NODE_ENV` is not `production`, the 6-digit OTP code is logged directly to stdout (`[OTP SIMULATOR] Phone: ..., Code: ...`) and exposed via `GET /api/auth/otp/:phone`. In `NODE_ENV=production` (which the Docker Compose `app` service sets) the code is neither logged nor exposed, so sign-up can only be completed in development/test mode. The `docker compose up --build` stack therefore serves the API and seeded admin login, but not new sign-ups.

## How to Run the Tests

### Single-Command Test Execution
Run the full test suite with:
```bash
npm test
```
Executes `vitest run --no-file-parallelism` and runs all 9 test suites (133 tests passing, 0 failures).

To execute a specific test file:
```bash
npx vitest run tests/health.test.js
npx vitest run tests/payment-concurrency.test.js
```

### Concurrency Rules and Test Suite
The concurrency safety test suite in `tests/payment-concurrency.test.js` proves:
1. **Idempotent Confirmations (Acceptance Check 11):** Repeating the exact same payment confirmation with an identical request identifier (`Idempotency-Key` header) charges the customer only once and returns the exact same cached response.
2. **Dual Simultaneous Payments (Acceptance Check 10):** Two concurrent payment requests of 800 DA sent against a 1,000 DA wallet balance result in exactly one successful transaction and one rejected transaction with an insufficient balance error, leaving a final balance of exactly 200 DA.
3. **Total Conservation Invariant (Acceptance Check 13):** Across mixed sequential and concurrent operations, the sum of all customer and shop wallet balances strictly equals the cumulative funds loaded by the admin.

## How AI Tools Were Used

Development follows an agentic workflow defined in `_docs/process.md` and `_docs/team/pm.md`.

### Agent Roles
1. **Product Manager (PM):** Grooms backlog tasks before any implementation begins. Using `_docs/task-template.md`, the PM defines clear goals, checkable acceptance criteria, explicit constraints, and isolates out-of-scope items into linked follow-up issues. The PM does not write code.
2. **Software Engineer:** Takes the groomed task specification, reviews context (`AGENTS.md`, `_docs/plan.md`), and implements the functionality strictly within the task boundaries. Enforces integer centime arithmetic, atomic database operations with row locking, and keeps external dependencies limited to `package.json`.
3. **Quality Assurance (QA) / Tester:** Implements automated test suites covering each acceptance check from `_docs/plan.md`, runs regression checks with `npm test`, and verifies edge cases before tasks are marked complete.

### How a Task Moves to Completion
1. A backlog task from `_docs/tasks.md` is selected or created as a GitHub Issue.
2. The PM agent structures and grooms the issue with verifiable acceptance criteria.
3. The engineer agent implements the code changes and accompanying automated tests.
4. The test suite is executed locally (`npm test`) to verify that all acceptance checks pass and no regressions exist.
5. Code is committed, pushed to `main`, and the GitHub issue is closed.

### What Was Actually Done
Tasks 1 through 7 were completely implemented, verified with automated tests, and closed (#6 through #12). For Task 9, payment confirmation idempotency, dual-payment concurrency, and platform balance conservation tests were implemented (`tests/payment-concurrency.test.js`). For Task 15, full-stack Docker Compose containerization (`docker compose up --build` with automatic migrations and admin seed) and a GitHub Actions CI workflow (`.github/workflows/ci.yml`) were implemented and verified with 133 passing tests across 9 test suites. The remaining tasks (#13, #14, #15, #16, #17, #18, #19, and the public deployment of #20) are deferred to a future version and tracked in milestone "M5 Later".

## Deployment

> **Not deployed yet.** This application is not currently hosted anywhere and there is no public URL. This section only documents the steps to deploy it to [Render](https://render.com). The steps have not been executed, so details of Render's dashboard may differ slightly from what is described here.

The repository already contains everything Render needs: a `Dockerfile` (builds the React frontend, then at container start runs migrations, seeds the admin account, and starts the server on port 3000) and a GitHub Actions CI workflow.

### Step 1: Prepare the repository
1. Make sure the code is pushed to GitHub (`main` branch) and `npm test` passes.
2. Create a free Render account and connect it to your GitHub account.

### Step 2: Create the PostgreSQL database
1. In the Render dashboard click **New +** → **PostgreSQL**.
2. Choose a name (for example `wallet-db`), a database name (for example `wallet_db`), the PostgreSQL version 16, and the same region you will use for the web service.
3. Click **Create Database** and wait until its status is **Available**.
4. On the database page copy the **Internal Database URL** (it starts with `postgres://`). Use the internal URL because the web service and the database are in the same Render region.

### Step 3: Create the web service from the Dockerfile
1. Click **New +** → **Web Service** and select **Build and deploy from a Git repository**, then pick this repository.
2. Set **Language / Runtime** to **Docker**. Render builds the image from the `Dockerfile` at the repository root, so no build or start command is needed (the `CMD` in the `Dockerfile` is used).
3. Choose the same region as the database and an instance type.
4. *Alternative:* if you prefer to deploy a prebuilt image, build and push it to a container registry (`docker build -t <registry>/wallet-app .` then `docker push <registry>/wallet-app`), and choose **Deploy an existing image from a registry** instead.

### Step 4: Set the environment variables
In the web service's **Environment** tab add:

| Variable | Value |
| :--- | :--- |
| `NODE_ENV` | `production` (serves the built frontend from `dist/`) |
| `PORT` | `3000` (the port the `Dockerfile` exposes) |
| `DATABASE_URL` | The **Internal Database URL** copied in Step 2 |
| `JWT_SECRET` | A long random secret (do not reuse the development default) |
| `ADMIN_PHONE` | Phone number of the initial admin account (default `0555000000`) |
| `ADMIN_PASSWORD` | A strong password for the admin account (default `Admin1234!` must not be used publicly) |
| `ADMIN_NAME` | Display name of the admin account (default `Platform Admin`) |

### Step 5: Run the migrations and the admin seed
The `Dockerfile` starts the container with:

```bash
npx drizzle-kit migrate && node src/scripts/seed-admin.js && node src/index.js
```

So on every deploy, Render automatically (1) applies all Drizzle migrations to the database, (2) creates the admin account if it does not exist (the seed is idempotent, so redeploying does not create duplicates), and (3) starts the server. No manual step is required.

To run them manually (for example after changing credentials), open the web service's **Shell** tab (available on paid instances) and run:

```bash
npx drizzle-kit migrate
npm run seed:admin
```

### Step 6: Verify the deployment
1. Wait for the deploy log to show `Server listening on http://localhost:3000` and the service to become **Live**.
2. Open `https://<your-service-name>.onrender.com/health` (the URL Render assigns to your service) and check that it returns `{"status":"ok"}`.
3. Log in with `POST /api/auth/login` using `ADMIN_PHONE` and `ADMIN_PASSWORD` and check that a token is returned.

### Known limitations for a public deployment
- **Simulated OTP:** with `NODE_ENV=production` the simulated one-time code is neither logged nor exposed by `GET /api/auth/otp/:phone`, so new customer or merchant sign-up cannot be completed on a production deployment until a real SMS provider replaces `sendOtp` (see `src/services/otp.js`). The admin account created by the seed is already verified and can log in.
- **Frontend:** only the React scaffolding exists; the customer, merchant, and admin interfaces are planned for a future version, so the deployed app exposes the API only.
- **Free-tier behaviour:** free Render web services spin down after inactivity and free PostgreSQL databases expire after a limited period; use a paid plan for anything lasting.
